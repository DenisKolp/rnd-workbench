# RnD Workbench — продуктовый контракт пилота

Дата фиксации: 31 августа 2026 года
Статус: рабочая цель разработки
Пилот: около 30 сотрудников, macOS и Windows

Архитектурные ограничения пилота:

- Windows-клиент реализуется на Electron; compact/full являются состояниями
  одного `BrowserWindow` и одного backend-процесса;
- общие доменные политики и интеграционный runtime по мере миграции реализуются
  на Java 21;
- Python/native сохраняется для Whisper, LLM inference, OmniVoice и другой
  ML-логики, где перенос в JVM ухудшает качество, задержку или доступность
  модельных runtime;
- неподтверждённая Windows- или Java-функция остаётся выключенной capability
  gate и не показывается как готовая.

## North Star

RnD Workbench становится простым входом в ежедневную работу сотрудника. Основной
интерфейс — компактный голосовой виджет с быстрым естественным диалогом. Полное
рабочее окно открывается для истории, источников, материалов, планов,
согласований и детальной настройки. Выбор моделей, поиск контекста, скиллы,
маршрутизация и последовательность действий по возможности остаются под капотом.

Пилот успешен, если участники встраивают помощника в реальные ежедневные
процессы, а не только демонстрируют отдельные функции.

## Пользователи и рабочий контур

Первый этап — внутренняя команда примерно из 30 человек. После подтверждения
качества и управляемости продукт должен масштабироваться на сотрудников всей
компании.

Целевой рабочий контур включает:

1. встречи в корпоративном мессенджере;
2. почту и календарь;
3. постановку и сопровождение задач в Jira и Kaiten;
4. поиск, создание и изменение знаний в Confluence;
5. создание и редактирование документов;
6. помощь в задачах разработки.

Интеграции вводятся по вертикальным пользовательским сценариям, но остаются
частями одного ассистента и общего контекста. Первая обязательная вертикаль:
`встреча → решения и поручения → черновики задач → согласование → Jira/Kaiten →
уведомление о результате`.

## Основной UX

- Компактный голосовой виджет является основным входом и открывается без
  создания второго экземпляра приложения.
- Пользователь может начать разговор, перебить ответ, переключиться в чат и
  одним действием открыть полное рабочее окно с тем же состоянием.
- В чате сохраняется полный ответ. Голосом произносится короткая версия с главным
  результатом и следующим действием.
- Отдельный режим диктовки работает по удержанию системной клавиши: нажатие
  начинает локальную запись, отпускание запускает Whisper и вставляет текст в то
  же активное поле без обращения к LLM. Защищённые поля и смена фокуса
  обрабатываются fail-closed; распознанный текст остаётся в черновике.
- Нормальный запрос не требует ручного выбора модели, скилла, источника или
  интеграции. Система показывает сделанный выбор и позволяет исправить его.
- Ошибка TTS, модели или интеграции не уничтожает уже готовый текст и не
  имитирует успешное внешнее действие.

## Политика автономности пилота

### Без подтверждения

- чтение доступного пользователю контекста;
- локальный поиск, анализ и транскрибация;
- ведение рабочей памяти и внутреннего контекста;
- подготовка планов, дайджестов, документов и черновиков;
- выбор локальной или разрешённой корпоративной модели по политике данных.

### Автоматически, но с уведомлением и возможностью отмены

- создание и изменение личных задач и напоминаний;
- обновление внутренних материалов RnD Workbench;
- классификация и раскладка информации по рабочим пространствам;
- запуск заранее разрешённых пользователем автоматизаций.

### Только после предпросмотра

- отправка сообщений и писем;
- создание и изменение календарных событий;
- постановка задач другим людям в Jira/Kaiten;
- публикация или изменение страниц Confluence.

### Всегда с явным подтверждением

- удаление и массовые операции;
- изменение прав доступа;
- публикация во внешнюю область;
- необратимые действия и действия с повышенным риском.

После пилота пользователь сможет выдать ограниченное постоянное разрешение на
конкретное действие, пространство, адресатов и срок. Глобальный режим «делать всё
без подтверждения» не является целью.

Текущая реализация применяет эту матрицу в общем Python integration hub и
повторно проверяет её Java 21 companion-командой `autonomy.decide`. В Java
передаётся только vendor-neutral категория действия без содержимого и
идентификаторов. Решение повторно проверяется непосредственно перед connector
call; расхождение блокирует adapter до внешнего вызова;
недоступность companion включает видимый Python fallback без снижения уровня
согласования.

## Политика моделей и данных

- Базовые разрешённые маршруты: локальные модели на устройстве и корпоративные
  модели/API.
- Внешние публичные API не используются для корпоративных данных пилота по
  умолчанию.
- STT, TTS, исходное аудио и локальное хранилище остаются на устройстве, если
  корпоративная политика явно не задаёт другой управляемый контур.
- Корпоративный маршрут получает только контекст, допустимый классификацией,
  областью задачи и правами сотрудника.
- Секреты не хранятся в SQLite, сообщениях, телеметрии или Git.
- Отсутствующий исполнитель интеграции возвращает проверяемую ошибку, а не
  фиктивный успех.

## Измеримые критерии пилотной готовности

Значения ниже являются стартовыми инженерными SLO и уточняются на эталонных
устройствах пилота.

### Голос и быстродействие

- переход виджета в состояние прослушивания: не более 300 мс после действия
  пользователя;
- конец короткой реплики → готовый транскрипт: p50 ≤ 1,2 с, p95 ≤ 2,5 с;
- конец реплики → первый слышимый ответ в прогретом локальном контуре: p50 ≤ 3 с,
  p95 ≤ 6 с;
- остановка звука после подтверждённого перебивания: ≤ 250 мс;
- TTS real-time factor: ≤ 0,45;
- обрезанные аудиосэмплы: 0; единый профиль голоса на всём ответе: 100%;
- голосовой ответ по умолчанию: одна законченная реплика до 220 символов; полный
  ответ доступен текстом. Один запрос к TTS исключает смену голоса между
  фрагментами;
- распознавание русского языка на чистой речи: WER ≤ 12%; на пилотном словаре и
  корпоративной терминологии: WER ≤ 20% до адаптации словаря.
- начало диктовки не отбрасывает уже пришедшие после key-down аудиоблоки;
  отпускание клавиши является границей фразы и не ждёт VAD-тишину.

### Надёжность и безопасность

- crash-free пользовательские сессии: ≥ 99%;
- ни одна подтверждённая внешняя операция не выполняется повторно после
  перезапуска;
- 100% внешних действий имеют инициатора, предпросмотр, статус и безопасный
  журнал без содержимого секретов;
- отказ TTS не теряет текстовый ответ; отказ API до первого токена может перейти
  на локальную модель с видимым уведомлением; после частичного ответа повторный
  запрос автоматически не отправляется;
- все маршруты данных и уровни классификации покрыты контрактными тестами.

### Ежедневная полезность

- не менее 70% участников активны каждую неделю;
- не менее 50% участников используют продукт минимум три рабочих дня в неделю;
- не менее 60% пилотной группы завершают хотя бы один сквозной рабочий сценарий
  в неделю;
- медианная субъективная оценка полезности — не ниже 4 из 5;
- не менее 80% голосовых запросов выполняются без перехода в настройки;
- время первого полезного результата после установки — не более 10 минут.

Метрики использования собираются только в агрегированном виде без текста
запросов, транскриптов, содержимого документов и секретов.

Текущая реализация хранит на устройстве allowlist числовых voice-метрик с
90-дневным сроком и жёстким пределом 20 000 строк: платформа, маршрут,
измерительный контур, результат и время. В интерфейсе и экспортируемом JSON
доступна только сводка за 14 дней без идентификаторов сессий и сырых событий.
Порог считается подтверждённым не ранее пяти измерений; до этого статус —
`insufficient_data`. Windows WebAudio отдельно измеряет готовность захвата,
оценённый конец речи, постановку первого блока в аудиоустройство, peak/clipping
и программный 12-мс fade при перебивании. Это не заменяет акустический замер
фактического звука внешним микрофоном и hardware QA.

Ежедневная полезность хранится отдельно как дневные суммы только для жёсткого
allowlist событий: запуск приложения, завершённый голосовой/текстовый запрос,
диктовка, импорт встречи и подготовка briefing. Дополнительно сохраняются одно
число времени до первого результата и текущая оценка полезности 1–5 без
комментария. В JSON выходят только 28-дневные агрегаты, а не даты, timestamps,
пути, названия, содержимое задач или идентификаторы. Эти per-device отчёты дают
вход для расчёта метрик 30 участников; сами по себе они не доказывают достижение
когортных процентов до проведения пилота.

Для crash-free SLO хранится отдельное content-free состояние жизненного цикла:
платформа, ограниченный внутренний идентификатор запуска и флаг active/clean.
Повторные start/quit идемпотентны; новый запуск переводит оставшуюся active
сессию в один unclean exit. В агрегаты и экспорт попадают только числа начатых,
штатных и нештатных завершений и их отношение — без run id, времени, текста,
путей или документов. Порог 99% становится блокирующим только после 20
наблюдаемых завершений; до этого проверка честно остаётся `unverified`.

Перед пилотным использованием macOS и Windows backend формируют одинаковый
content-free preflight из двенадцати проверок. Неработающие LLM, STT, TTS,
хранилище или проваленный голосовой SLO блокируют устройство; неподтверждённый
микрофон, voice SLO и crash-free выборка помечаются `unverified`; подтверждённая
надёжность ниже 99% блокирует устройство. Отсутствие production коннекторов,
подписи или Java companion остаётся видимым `warn`. Ни один из этих статусов не
заменяет чистую установку и device smoke-test.

Поверх preflight обе платформы формируют одинаковый content-free быстрый старт.
Он не хранит отдельный профиль и не читает рабочее содержимое: по техническим
статусам и 28-дневным агрегатам выбирается ровно один следующий шаг — получить
первый результат, проверить голос, импортировать встречу или подготовить
сводку. Четыре этапа отображаются только в полном диагностическом контуре;
после выполнения блок остаётся компактным подтверждением завершения.

## Порядок технической реализации

1. Инструментировать и стабилизировать компактный голосовой контур.
2. Отделить кроссплатформенное ядро от macOS-адаптеров и подготовить Windows
   shell/упаковку.
3. Завершить автоматическую маршрутизацию local/corporate и отказоустойчивость.
4. Подключить к готовому безопасному API адаптеров первый production-маршрут
   встреча → задачи и проверить reconciliation на корпоративном стенде.
5. Подключать почту/календарь, Jira/Kaiten, Confluence и корпоративный мессенджер
   по доступным тестовым API и правам.
6. Добавить управляемую диагностику, onboarding, обновления и сбор пилотной
   обратной связи.

## Внешние зависимости и честные блокеры

Для настоящих корпоративных действий потребуются тестовые endpoint, схема
авторизации, права сервисного/пользовательского приложения и владельцы API для
мессенджера, почты, календаря, Jira/Kaiten и Confluence. Пока доступов нет,
разрабатываются интерфейсы адаптеров, контракты, безопасные предпросмотры и
локальные тестовые исполнители. Они не считаются реальной интеграцией и не могут
возвращать производственный статус `success`.

До подключения eXpress Recordings Bot/BotX первая вертикаль имеет проверяемый
fallback-вход через локальный пакет (legacy alias `synapse`): однозначный
быстрый набор из транскрипта, описания и вложений либо расширенный каталог/ZIP
версии 1.0 с `manifest.json` и metadata. Импорт проверяет пути, размеры и
SHA-256, сохраняет provenance, строит решения, поручения, риски, вопросы,
повестку следующей встречи и только локальные черновики продолжений. Этот режим
явно обозначается как `LOCAL_PACKAGE_IMPORT` и не выдаётся за подключённый
корпоративный API.

Повторяющиеся встречи объединяются только по явному series ID из нормализованной
metadata (`series_id` или совместимый `group_chat_id`). Подготовка следующей
встречи использует не более 12 встреч этой серии и автоматически строит
сравнение с предыдущей; при отсутствии ID остаётся в границах выбранной встречи.
Название и состав участников не используются как неявный идентификатор.

## Definition of Done цели

Цель считается достигнутой, когда macOS- и Windows-сборки проходят единый набор
контрактных и end-to-end проверок, голосовые SLO подтверждены на пилотном наборе
устройств, сквозная вертикаль встречи и задач работает с реальными тестовыми
корпоративными API, политика автономности соблюдается, 30 участникам доступен
onboarding и диагностика, а результаты пилота можно оценить по указанным
метрикам без сбора рабочего содержимого.
