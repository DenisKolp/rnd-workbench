# ADR-0001: Java 21 core между клиентскими оболочками и Python inference

- Статус: принято для инкрементального внедрения
- Дата: 2026-08-31
- Область: кроссплатформенная архитектура пилота RnD Workbench

## Контекст

Пилот рассчитан примерно на 30 сотрудников с macOS и Windows. Основной сценарий
— быстрый компактный голосовой виджет с переходом в полное рабочее окно. Windows
клиент должен использовать Electron; существующая macOS оболочка остаётся на
Swift, пока нативный voice path даёт преимущество по задержке и стабильности.

При этом политики данных, маршрутизации моделей, автономности и внешних действий
не должны расходиться между клиентами. ML inference уже реализован в Python и
использует нативные библиотеки Whisper/MLX/OmniVoice. Перенос этого кода в JVM не
даёт продуктового выигрыша и создаёт риск для качества голоса.

## Решение

Постепенно вводим Java 21 core с чистыми платформенно-независимыми доменными
правилами:

- классификация данных до формирования prompt/context;
- выбор локальной или корпоративной модели с local-first fallback;
- внешний маршрут выключен в пилоте по умолчанию;
- матрица автономности и подтверждений;
- общий контракт интеграционных действий и metadata идемпотентности.

Целевая зависимость выглядит так:

```text
┌─────────────────────┐       ┌──────────────────────┐
│ macOS: Swift shell  │       │ Windows: Electron    │
│ widget + full UI    │       │ widget + full UI     │
└──────────┬──────────┘       └───────────┬──────────┘
           └──────── versioned local IPC ─┘
                              │
                    ┌─────────▼─────────┐
                    │ Java 21 core      │
                    │ policy + actions  │
                    └─────────┬─────────┘
                              │
                    ┌─────────▼─────────┐
                    │ Python bridge     │
                    │ STT / LLM / TTS   │
                    └───────────────────┘
```

Это целевая граница, а не заявление о том, что существующие Swift/Python вызовы
уже мигрировали. Внедрение идёт вертикальными инкрементами с контрактными тестами
и временным fallback на текущий путь.

## Почему голосовой тракт остаётся вне Java core

Компактный виджет должен начать слушать не позднее 300 мс, остановить звук при
перебивании не позднее 250 мс и дать первый слышимый ответ в прогретом локальном
контуре с p50 не более 3 с. Поэтому:

- захват/воспроизведение аудио и barge-in принадлежат оболочке и Python bridge;
- аудиочанки не проходят через Java сериализацию;
- Whisper, локальная LLM и OmniVoice остаются в Python/native runtime;
- Java принимает решение о допустимом маршруте до inference и получает только
  необходимую служебную телеметрию без текста/аудио.

## Политика маршрутизации пилота

| Класс данных | Локальная модель | Корпоративная модель | Внешняя модель |
|---|---:|---:|---:|
| `PUBLIC` | да | при разрешённой области | выключена по умолчанию |
| `PERSONAL` | да | при разрешённой области | нет |
| `CORPORATE_INTERNAL` | да | при разрешённой области | нет |
| `CONFIDENTIAL` | да | при разрешённой области | нет |
| `RESTRICTED` | да | нет | нет |

`AUTO` сначала выбирает доступный локальный маршрут. Если он недоступен,
разрешена корпоративная модель только после проверки классификации и области
доступа. Для явно выбранного корпоративного маршрута локальный fallback допустим
только до первого вывода; после частичного ответа повторная отправка запрещена.

Будущее включение external feature flag не обходит ограничения: внешний маршрут
может принять только `PUBLIC` данные и требует явного согласия на конкретный
запрос.

## Контракт внешнего действия

Каждое действие несёт:

- логический `actionId`, connector/operation и user-visible intent;
- вид действия для выбора уровня автономности;
- классификацию данных и неизменяемый JSON-compatible payload без секретов;
- actor/origin/request correlation;
- idempotency key, SHA-256 fingerprint запроса, время выдачи и номер попытки.

Исполнитель production-интеграции обязан атомарно claim-ить key/fingerprint до
сетевого вызова и сохранять безопасный результат после него. Повтор с тем же
key/fingerprint возвращает сохранённый результат; тот же key с другим
fingerprint отклоняется.

Этот инкремент добавляет SQLite journal в Java core. Атомарный `INSERT OR IGNORE`
выдаёт ровно один UUID claim token. Незавершённый claim после restart остаётся
`IN_PROGRESS` и не получает автоматический lease retry: такое повторение могло бы
продублировать уже состоявшийся внешний effect. После сверки с внешней системой
connector сохраняет outcome/result code или администратор разрешает конфликт.

SQLite выбран вместо H2, потому что это embedded transactional store без
отдельного сервера, одинаково работающий через JDBC на macOS и Windows. Файл
можно диагностировать стандартными инструментами, а в будущем при необходимости
читать из Python/Electron tooling. Runtime-зависимость закреплена как
`org.xerial:sqlite-jdbc`; серверная СУБД и её эксплуатация для desktop pilot не
нужны.

Journal не хранит action payload, prompt, response body, документы, аудио или
credentials: только key, fingerprint, correlation, claim token, timestamps и
короткие машинные metadata результата. Это также исключает попадание content и
секретов в diagnostic logs Java core — входные frames и exception text не
логируются.

API-ключи, cookies, пароли и bearer tokens не входят в envelope. Их получает
коннектор из системного vault/credential manager.

## Формат связи

Реализован executable Java-процесс с UTF-8 JSONL stdio framing: он не открывает
порт и одинаково запускается из Electron и Swift. Каждый request/response несёт
версию `1.0`, строгий type и correlation ID. Duplicate/unknown/missing fields,
неизвестная версия или команда отклоняются безопасной ошибкой без отражения
входного content. Размер line, JSON string и nesting ограничены.

Публичный контракт включает `route.decide`, `action.claim`, `action.inspect`,
`action.complete` и `health.check`; JSON Schema находятся в
`core-java/src/main/resources/schema`, а
правила и примеры — в `core-java/docs/ipc-v1.md`. JSON сериализуется
детерминированно: свойства и map keys сортируются, dates имеют ISO-8601 вид.

Loopback transport остаётся допустимым будущим вариантом только с
аутентификацией сессии, ограничением размера сообщений и запретом прослушивания
внешнего интерфейса.

## Последствия

Положительные:

- одна тестируемая политика для macOS и Windows;
- Java подходит корпоративной эксплуатации и будущим connector workers;
- UI и ML runtime меняются независимо;
- риск большого переписывания отсутствует.

Ограничения:

- macOS/Windows Python bridge использует Java core для routing и durable
  claim/inspect/result; production-коннекторы и их API пока не подключены;
- обе desktop-сборки выросли из-за bundled `jlink` runtime и Java libraries;
- версия схемы и совместимость процессов становятся отдельным контрактом;
- SQLite journal не может атомарно коммитить транзакцию вместе с произвольным
  Jira/Kaiten/Confluence API; зависшие claims требуют connector reconciliation.

## План внедрения

1. Подключить production-коннекторы к готовому claim/inspect/result boundary и
   реализовать их idempotency lookup на корпоративных тестовых стендах.
2. Провести crash/restart reconciliation soak-test до production writes.
3. После пилотного soak-test удалить дублирующие политики из оболочек.
